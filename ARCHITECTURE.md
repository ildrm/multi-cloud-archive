# Architecture and feasibility

The application is a Rust modular monolith. `crates/engine` owns encrypted chunking, verification, immutable manifests and restore. `crates/app` owns SQLite jobs, browser OAuth, account-scoped native credentials and real cloud adapters. `apps/desktop` supplies Dioxus components/CSS, native pickers and bounded worker communication; `apps/cli` shares the same services. Dioxus 0.7.3 and compatible 0.7.10 subcrates are locked, using the system WebView. The framework remains provisional pending the mandatory cross-platform tests. See the [platform guide](https://dioxuslabs.com/learn/0.7/guides/platforms/) and [mobile guide](https://dioxuslabs.com/learn/0.7/guides/platforms/mobile/). No experimental native renderer or project-hosted server is used.

## Highest-risk gates

1. Demonstrate two distinct Google identities, scoped recovery on a fresh installation and visibility across desktop and Android client identities. Google describes [cross-client authorization](https://developers.google.com/identity/protocols/oauth2/cross-client-identity), but that alone does not prove this application's Drive file discovery and recovery behavior. Android authorization must use an appropriate native flow rather than assuming desktop redirects work; Google's [migration guidance](https://developers.google.com/identity/protocols/oauth2/resources/oob-migration) describes Android authorization.
2. On Windows, Debian, actual RHEL, macOS, and Android: prove rendering, native file selection, protected credentials, streaming upload/download, and restoration. Windows compilation and local-engine tests are available; live provider and other-platform evidence is still absent. Android needs SAF stream abstractions, native token acquisition, Keystore and lifecycle integration; desktop path-based code is not Android support.
3. Specify and independently review key management, authenticated immutable metadata, crash-safe commit, fresh-device recovery, and safe restore before treating any archived data as protected. Source deletion and garbage collection stay disabled until their separate safety conditions are met.

## Implemented boundary

`cloudweave-domain` is an in-memory model and advisory per-object selection function. An account has an internal ID, provider-issued identity and opaque credential reference; reconnect requires the same identity. Quotas are explicitly shared by quota domain. The planner subtracts reserve and in-flight reservations, rejects unknown free capacity, and requires different provider kinds for provider-loss protection. It does not authenticate, store credentials, establish whether inputs are truthful, check quota freshness, measure provider health, or persist or atomically reserve space. Callers must establish resource ownership, map correlated failure domains correctly, and revalidate and reserve transactionally before upload. In particular, a provider kind is a conservative initial stand-in, not a complete failure-domain model.

The engine and app implement a one-copy archive slice, not the advisory planner's redundant multi-account pool. The experimental format and bounded parser/decompressor limits are in FORMAT.md. Restore requires a kit carrying actual remote IDs and validates authenticated relative paths before writing to a fresh staging directory. Imported local-root hints are not opened automatically: the user must select an existing local folder. No source deletion or garbage collection is implemented. A second source pass detects changes but is not a filesystem snapshot. Empty directories, portable filesystem metadata, selective restore and cross-snapshot deduplication are incomplete.

Job phase transitions use SQLite WAL and FULL synchronous transactions. A process lock prevents simultaneous instances sharing one catalog. Startup marks unfinished jobs as interrupted for manual retry; no promise of per-byte restart/resume is made. Immutable upload failure can leave harmless unreferenced encrypted objects. Bounded UI progress drops intermediate samples when saturated and delivers terminal results from workers, never blocking the UI event thread. Cryptographic and network work stays off the UI thread.

Crypto uses Argon2id and XChaCha20-Poly1305, independent BLAKE3-derived subkeys, fresh random nonces, passphrase and recovery envelopes. This composition has agent engineering review only; independent human security review and release signing remain required. Native dependencies include zstd, SQLite, WebView2 and renderer/platform libraries; the dependency graph is not exclusively Rust. There is no released format compatibility guarantee yet.

# Threat model (initial, incomplete)

The intended system must defend against compromised or revoked cloud credentials, malicious or corrupt remote content, hostile manifests, rollback, partial outages, unsafe restore paths, stolen locked devices and sensitive diagnostic output. Malware controlling an unlocked device is outside the intended protection boundary. Object counts, sizes, timing and provider identity may remain visible to storage providers. No cryptographic design or security review has yet established these protections.

Implemented mitigations include authenticated chunk/manifest encryption, domain-separated keys, bounded KDF/parser/decompression inputs, full object read-back verification, safe relative restore paths, new-file restore, native per-account token protection, exact OAuth callback correlation, disabled HTTP/WebView navigation redirects and redacted request Debug output. Provider identity is confirmed through official APIs; quotas can be shared or stale and are observations rather than guarantees. Source removal, remote deletion and garbage collection are not implemented. The archive pipeline currently offers only one copy and cannot survive its provider's loss.

Residual gaps: independent human audit, real cloud and cross-client recovery tests, coherent filesystem snapshots, rollback prevention, human assistive-technology validation, Android secret/stream/lifecycle bridges, Linux encrypted credential fallback, dependency advisory/license scanning and signed release/update infrastructure. See SECURITY.md for intentionally visible metadata, plaintext recovery exports and partial restore output. A stolen recovery kit alone should not reveal the vault key; the secret export or passphrase must be protected independently. Endpoint compromise, malicious local administrators and malware operating on an unlocked device are outside the intended defense boundary.
